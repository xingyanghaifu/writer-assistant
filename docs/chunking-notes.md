# 各平台分块策略实测笔记（阶段 11.5b）

本文件记录四个站点的分块（chunking）策略选择依据。**所有选择器与策略都集中在
`src/renderer/adapters/<site>.ts`**，站点改版时只需改这一个文件。

---

## 为什么需要分块

四个平台对单条消息都有长度限制，且长文本行为差异很大：

| 平台 | 单条粘贴上限（观察值） | 超限行为 | 多轮记忆 |
|---|---|---|---|
| DeepSeek | 较长（数万字符） | 直接接受 | 一般，倾向于记住最近 2–3 轮 |
| ChatGPT | 约 10000 字符 | 超出部分转为**附件**，不再作为对话上下文 | 好 |
| Claude | 较长 | 直接接受 | 对 XML 标签结构感知强，但长上下文中段易丢 |
| Gemini | 较短 | 可能压缩或截断 | 弱，多消息场景可能遗忘早期内容 |

> 上述数值随平台调整而变化，**代码中一律留出余量**（见各 `maxChunkSize`）。

---

## 分块模式（`ChunkingMode`）

`src/types/adapter.ts` 定义三种模式：

1. **receive-then-process**（接收-处理分离，默认）
   先逐段发送并只要求回执，最后一条统一处理。
   优点：模型对"全部内容"有整体感知，输出质量最好。
   缺点：轮次多，对多轮记忆要求高。

2. **summary-first**（摘要优先）
   每段发送时即要求产出摘要，最后基于**全部摘要**统一处理。
   优点：规避长上下文遗忘，即使早期消息被丢弃仍保留要点。
   缺点：二次加工有信息损耗，细节可能丢失。

3. **per-chunk-independent**（逐块独立）
   每段独立处理，最后合并结果。
   优点：最稳定，不受记忆影响。
   缺点：跨段一致性问题（人名、称谓、时态）。

## 各站点最终选择

### DeepSeek —— `receive-then-process`，块 3000 字
- **理由**：对 `〖〗` 结构化前缀响应好，能稳定遵守"只回执不处理"的指令。
- **参数**：`maxChunkSize: 3000`、`overlap: 200`、`requireSummary: true`
- **前缀/后缀**：`〖接收〗` / `〖仅回执〗`
- **验证**：分段回执稳定，未出现提前处理的情况。

### ChatGPT —— `receive-then-process`，块 5000 字
- **理由**：指令服从度高，能准确区分"回执"与"处理"两个阶段。
- **关键约束**：**块大小必须 < 10000 字符**，否则内容会转为附件，
  附件内容不进入对话上下文，模型将"看不见"该段。
  取 5000 留一倍余量（中文一个汉字占 1 字符，但标点与换行也计入）。
- **参数**：`maxChunkSize: 5000`、`overlap: 200`、`requireSummary: true`

### Claude —— `receive-then-process` + XML 标签，块 4000 字
- **理由**：Claude 对 XML 结构标签的理解显著优于纯文本分隔符，
  用 `<segment index="N" total="M">` 包裹每段可明显提升结构感知。
- **关键约束**：多轮分块时**容易遗忘前文**，因此必须开启
  `requireSummary: true`，并在后续每一段携带 `<previous-summary>`。
- **参数**：`maxChunkSize: 4000`、`overlap: 200`
- **降级方案**：若发现摘要仍丢失细节，可改为 `per-chunk-independent`。

### Gemini —— `summary-first`，块 3000 字
- **理由**：多消息场景下早期消息可能被压缩或遗忘，
  `receive-then-process` 的回执阶段容易被跳过，导致"提前处理"。
- **做法**：发送每段时**直接要求只输出摘要**（不回执），
  最后基于全部摘要统一处理。完全不依赖多轮记忆。
- **参数**：`maxChunkSize: 3000`、`overlap: 100`、`requireSummary: true`
- **降级方案**：若摘要粒度太粗，改为 `per-chunk-independent` 并对每段
  独立执行任务，最后在前端合并。

## 通用参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `maxChunkSize` | 3000 | 单块目标字数（各站点分别覆盖） |
| `overlap` | 200 | 块间重叠，避免在断句中间切断语义 |
| `requireSummary` | true | 是否要求产出摘要 |
| `CHUNK_INTERVAL_MS` | 500 | 相邻块发送间隔（合规要求，避免高频） |
| `STREAM_IDLE_MS` | 1500 | 流式空闲判定 |
| `CHUNK_TIMEOUT_MS` | 120000 | 单块超时 |

## 分块边界优先级

`src/types/chunking.ts` 的 `splitIntoChunks` 按以下优先级选切点：

1. **章节边界**（`第X章`、`Chapter N`）—— 最优，语义完整
2. **段落边界**（空行）—— 次优
3. **场景切换**（`次日`、`与此同时`、`另一边` 等）—— 可接受
4. **硬切**（按字数强断）—— 最后手段，会尽量避开引号内与句子中间

重叠部分由 `mergeOverlapping` 在合并结果时去重，避免重复计入。

## 站点改版应对

**只需修改 `src/renderer/adapters/<site>.ts` 中的选择器常量：**

```ts
const INPUT_SELECTORS = [...]      // 输入框
const SEND_SELECTORS = [...]       // 发送按钮
const ASSISTANT_SELECTORS = [...]  // 助手回复容器
```

主进程**只执行脚本、不理解站点细节**，因此站点改版不会波及
`src/main/**` 任何文件。脚本本身由 `adapters/common.ts` 生成，
带完整 try/catch 容错，找不到元素时返回 `null`/`false` 而非抛异常。

### 如何快速定位失效的选择器

容错的代价是**失败是静默的**。为此内置了自检工具：

**设置 → 适配器自检 → 检测当前站点**

它会：
1. 逐个选择器报告命中数（未命中的标红）—— 直接告诉你哪一行要改
2. 显示登录态，区分「未登录」与「选择器过期」两种失败原因
3. 可选写入测试，验证插入链路（不会发送）

> 检测的是**当前站点**（其他站点的页面未加载，检测无意义）。
> 请先切到目标站点并等页面加载完成再点检测。

## 合规红线

- 块间隔固定 500ms，**不做高频自动化滥用**
- 不绕过登录、验证码、风控
- 只向**隐藏的后台会话**发送，绝不自动发送用户可见的当前对话
- 所有 AI 输出均标注「AI 生成，仅供参考」
